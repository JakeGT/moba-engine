# HUD polish: MSDF text, health bars, combat text (R7a)

Captured 2026-10-28 on the development workstation, not a CI runner: the same machine, driver
and method as [perf/0011](0011-render-graph.md).

- GPU: NVIDIA GeForce RTX 5070 Ti, driver 615.78.08 (`nvidia_icd.json`); CPU AMD Ryzen 7
  9800X3D; Linux 7.3.0-2-cachyos, Wayland.
- Window `MOBA_WINDOW_SIZE=1920x1080`, vsync off, validation off, quality High.
- The frame is light enough that the GPU stays in a low power state (perf/0011 read P8). All
  µs figures are at those clocks.

## What changed in the UI pass

| | Before (`main` at `e2972de`) | After (R7a) |
|---|---|---|
| Text | 5×7 bitmap glyphs from the 128×64 RGBA atlas, nearest filtering | MTSDF glyphs from a 512×208 RGBA8 atlas (416 KiB), linear filtering, derivative anti-aliasing |
| Vertex | 36 bytes | 48 bytes (`mode`, packed `outline` colour, two `params`) |
| Descriptors | one combined image sampler | two (pixel-art atlas + font atlas), same set |
| Push constants | 8 B, vertex stage | 16 B (adds the font's distance range), vertex + fragment |
| Fragment work | one atlas read | per-mode branch: solid, atlas, MSDF fill + outline, soft shadow, or radial sweep |
| Draws | one | one (unchanged) |

Glyph quads now include the distance margin (0.125 em on each side), so text covers more
pixels than the tight bitmap cells did. Shadowed and outlined text draws a second quad per
glyph.

## CPU-side presentation state

- `HudFx` keeps fixed-capacity state: up to 96 tracked units in an `ArrayVec` (damage ghosts)
  and a 360-slot combat-text ring: 8 spawns per snapshot × (8 ticks of render lag + the
  36-tick longest life + 1), so a full budget every snapshot is never overwritten before it
  has faded. Each processed snapshot keeps its 8 most important numbers. The HUD draws the
  newest 48 per frame and culls off-screen ones.
  `teamfight_combat_text_stays_within_a_vertex_budget_without_allocating` checks that a full
  ring stays within 48 × 60 vertices and allocates nothing.
- Allocation tests (the client's counting allocator) check that these steady states allocate
  nothing:
  - `hud::fx` `steady_state_observe_and_draw_queries_do_not_allocate`: 100 observes of a
    40-hero snapshot, plus screen updates and text and ghost queries;
  - `match_hud_has_zero_steady_state_allocations`: the full lobby/match HUD with scoreboard
    and shop;
  - `network_hud_has_zero_steady_state_allocations`: the loading screen;
  - `local_hud_has_zero_steady_state_allocations`.
- Text is still formatted into the 256-byte stack `HudString`.

## Reading the numbers

- **The normal HUD costs the same on the GPU:** 5–6 µs, against 5 µs before. The MSDF
  branch, the second texture and the larger quads are within 1 µs at 1080p.
- **The worst case adds about 11 µs p50 and 20–35 µs p95.** That HUD covers much of the screen
  at 2× scale, with every glyph drawn as a margin-padded quad. It is 0.05–0.09 ms of a 6.9 ms
  p95 budget. If text-heavy screens grow, the cheapest fixes are tighter glyph quads (trim the
  margin when a style has no outline or shadow) or a separate text draw with its own pipeline
  to drop the mode branch.
- **CPU:** `render_*` rises by about 0.02 ms in the overview scene, from the 33 % larger
  vertex upload and the extra shadow quads. It is unchanged in the follow scene and within
  noise in the worst case.
- All of this is far below the roadmap's per-feature budgets. Low and min-spec numbers (UHD
  620, MoltenVK) do not exist yet (#9/#127).

## R7b: render-to-texture portraits and the baked minimap

Captured 2026-10-29 on the same workstation, driver and settings as above (RTX 5070 Ti,
driver 615.78.08, 1920×1080, vsync off, validation off), on the follow camera
(`MOBA_SERVER=local`, `MOBA_WARMUP_TICKS=960`, `MOBA_SMOKE_FRAMES=3000`,
`MOBA_HERO_MODELS=sentinel-skinned`), 2,940 measured frames per run. "Off" is the same
build with `MOBA_PORTRAITS=off MOBA_MINIMAP_BAKE=off`, which draws the R7a HUD (its networked
capture matches the R7a golden exactly).

### What R7b adds to the frame

| | R7a | R7b |
|---|---|---|
| Passes | scene, composite, ui (+ capture) | + `portraits` and `minimap`, only in frames that re-render them |
| Offscreen images | none | portrait strip 2048×128 and minimap 512×512 in the HDR format, a D32 depth buffer each: 6 MiB (`R16G16B16A16_SFLOAT`) or 4 MiB (`Low`), allocated once with the renderer |
| Per-frame buffers | main view | + one camera/instance/bone set per image and frame in flight: 1,024 instances and 1,024 joints each, about 0.5 MiB in all |
| Graph variants | 2 | 8 (capture × which offscreen passes run), compiled at creation |
| UI vertex | 48 bytes | 52 bytes (`image`) |
| UI descriptors | 2 combined image samplers | 4 (+ one per `UiImage` slot) |
| UI push constants | 16 B | 32 B (+ exposure, saturation, sRGB flag) |

The UI pass now names both offscreen images in every frame (a fragment sampled read). A frame
that did not re-render one gets an execution-only barrier for it in the same layout; a frame
that did gets the colour-write → sampled-read transition. Both are in the headless graph
tests.

"Off" round 1 ran with the GPU in a lower clock state (its scene pass read 0.105 ms against
0.050–0.052 in every other run), so it is left out of the comparison. The frame interval
stayed display-paced at 4.17–4.18 ms p50 in every run. The minimap bake runs once per map bind
in normal play (before the measured window); the stress run re-bakes it every 10 frames to
measure it.

### Reading the numbers

- **A portrait update costs 8–9 µs of GPU time**, in the frames that carry one (10 a second
  on High, so about 0.09 ms per second; on Low only when the heroes change). It draws up to 16
  heroes, each with its own skinned draw, into a 2048×128 target.
- **A minimap bake costs 8–9 µs**, once per map load. The default map has no walls or props;
  each prop or wall is one more instance in the same instanced draws.
- **The UI pass goes from 6 µs to 9 µs p50** with the portrait (104×104), the minimap image
  (168×168, four taps and an AgX evaluation per pixel) and the fog grid (up to 24 rows of
  rectangles). With the scoreboard's ten small portraits it is 11 µs.
- **CPU:** building the portrait strip and its animators adds about 1–4 µs to `cpu_*` p50
  (more at 60 Hz). `render_*` is within the run-to-run noise. The portrait update, the bake
  decision and the HUD with images allocate nothing (`portrait_strip_builds_each_cell_without_allocating`,
  `match_hud_has_zero_steady_state_allocations` with every image on).
- Like the R7a numbers these are far below the roadmap budgets, and Low/min-spec (UHD 620,
  MoltenVK) numbers do not exist yet (#9/#127). The portrait cells are 128 pixels: at a 2× UI
  scale the hero-panel portrait (208 pixels) is magnified and slightly soft; a larger strip is
  one `RenderConfig::with_ui_image_size` away.
