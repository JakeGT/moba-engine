# Vendor SDK features (DLSS, NRD, RTXDI, SHaRC, Streamline, FSR 4, XeSS)

The renderer can compile in NVIDIA, AMD and Intel SDKs behind cargo features
([ADR-0020](../adr/0020-next-gen-foundations.md) §6 and amendment 6). They are **off by
default**: `cargo build` needs no proprietary SDK, and public releases ship that open build only
([RELEASE.md](../../RELEASE.md) step 8). In N0 a back end is only probed at start-up; nothing
reaches the frame until its phase (N1 upscalers, N7/N8 lighting, N9 frame generation).

## Features

The features live on `moba-render` and are forwarded with the same names by `moba-client` and
`moba-engine` (under `render`). No server crate can reach them (the layering check).

| Feature | Slot | SDK | Builds on | Run-time binary |
|---|---|---|---|---|
| `fsr3` (default) | upscaler | none in N0 (FSR 3.1 shaders arrive in N1) | all | — |
| `dlss` | upscaler (1st) | DLSS 310.9.16 | Linux, Windows | NGX loads `libnvidia-ngx-dlss.so.310.9.16` / `nvngx_dlss.dll` |
| `fsr4` | upscaler (2nd) | FidelityFX SDK 2.4.0 | Linux, Windows (headers) | `amd_fidelityfx_{loader,upscaler}_vk.dll`, Windows only |
| `xess` | upscaler (3rd) | XeSS 3.0.2 | Linux, Windows (headers) | `libxess.dll`, Windows only; never selected in N0 (see below) |
| `nrd` | denoiser | NRD 4.18.0 (built from source with CMake) | Linux, Windows | none (static library) |
| `rtxdi` | direct lighting | RTXDI 3.1.0 | all | none (shader library) |
| `sharc` | radiance cache | SHaRC 1.8.3 | all | none (shader headers) |
| `streamline` | frame generation | Streamline 2.14.16 | Linux, Windows (headers) | `sl.interposer.dll`, Windows only; N0 only looks for it (see below) |

Aggregates: `nvidia = dlss, nrd, rtxdi, sharc`; `vendor-sdks = nvidia, fsr4, xess`;
`dlss-fg = dlss, streamline`. `fsr4` is development-only (ADR-0020 Q6).

## Fetching

```bash
scripts/fetch-sdks.sh --only dlss,rtxdi      # or --only vendor-sdks,dlss-fg, or no option for all
scripts/fetch-sdks.sh --present-features     # prints the features whose SDKs are fetched
```

On Windows: `scripts\fetch-sdks.ps1 -Only dlss,rtxdi` (or Git Bash with the `.sh`).

- `vendor-sdks.toml` pins every archive: an official GitHub release asset or tag/commit
  archive, its SHA-256 (cross-checked against GitHub's release `digest` where one is
  published), and the SHA-256 of its licence file. Submodules and CMake downloads (RTXDI's
  library, NRD's ShaderMake and MathLib) are entries of their own, unpacked where the SDK's
  build expects them.
- SDKs land in `${MOBA_SDK_DIR:-target/vendor-sdks}/<name>-<tag>/`; archives are cached in
  `downloads/` and re-verified on reuse. A `.moba-sdk-sha256` stamp marks a verified unpack.
  A relative `MOBA_SDK_DIR` is relative to the workspace root, in the scripts and in
  `build.rs` alike.
- `--only` takes entry names, feature names and the aggregates; any other name is an error.
  Zip archives need `unzip` or `bsdtar` (GNU tar cannot read them); the PowerShell script
  uses Windows' own `%SystemRoot%\System32\tar.exe`.
- **A changed licence fails the fetch.** The new text is kept as `changed-licence-*` beside
  the SDK; read it, and the PR that updates `licence_sha256` records the re-read.
- The script only downloads and unpacks. Nothing inside an archive is ever run by it.

## Building

```bash
cargo build -p moba-client --features dlss,rtxdi,sharc
```

- `build.rs` reads `MOBA_SDK_DIR` (default `target/vendor-sdks`) and **never downloads**. A
  missing or stale SDK fails the build with the fetch command to run.
- FFI declarations are generated by `bindgen` into `OUT_DIR` from the fetched headers; nothing
  derived from an SDK is committed. `bindgen` needs **libclang** (set `LIBCLANG_PATH` if it is
  not found; the runner images and Arch's `clang` package have it).
- `nrd` also needs **CMake 3.30+** (`CMAKE` overrides the path) and the **Vulkan SDK's `dxc`**
  (on `PATH`, or `%VULKAN_SDK%\Bin\dxc.exe` on Windows). The configure step is fully
  disconnected: `FETCHCONTENT_FULLY_DISCONNECTED=ON`, ShaderMake and MathLib from the fetched
  entries, `NRD_NRI=OFF`, `SHADERMAKE_FIND_DXC=OFF`, `SHADERMAKE_FIND_FXC=OFF`,
  `SHADERMAKE_FIND_DXC_VK=ON`, SPIR-V embeds only, static library. `dxc --version` must
  succeed, not just be found (on Linux the Vulkan SDK's `dxc` needs its `lib` directory on
  `LD_LIBRARY_PATH` for `libdxcompiler.so`). NRD's configure step writes
  `Shaders/NRDConfig.hlsli` into its source tree, so `build.rs` runs CMake on a copy of NRD;
  the fetched SDK is never written to. NRD is built once per pin, target, profile and
  toolchain in `<build-dir>/<profile>/vendor-build/nrd` (cargo's build dir: the target dir
  unless `CARGO_BUILD_BUILD_DIR` moves it), not in `OUT_DIR`, so every feature set and clippy
  reuse it. A stamp written last records what it was built from: the SDK pins, the
  `cmake --version` and `dxc --version` lines, every CMake definition, and the environment
  the `cmake` and `cc` crates read (`CMAKE`, `VULKAN_SDK`, `CMAKE_GENERATOR`,
  `CMAKE_TOOLCHAIN_FILE`, `CMAKE_PREFIX_PATH`, and `CC`, `CXX`, `CFLAGS`, `CXXFLAGS`, `AR`
  in their plain, per-target and `TARGET_` forms). Anything else is rebuilt from scratch, and
  only the libraries and the stamp are kept. The C++ compiler's own version is not in the
  stamp: after a compiler upgrade, delete `vendor-build/nrd`.
- Linking: NGX's static library (`libnvsdk_ngx.a` plus `stdc++`/`dl` on Linux,
  `nvsdk_ngx_d.lib` on Windows); NRD statically with ShaderMake's `ShaderMakeBlob`, which a
  static NRD needs for its shader lookup (plus `stdc++`, or `c++` on Apple targets);
  FSR 4 and XeSS are opened at run time with `libloading`, so a feature build still starts
  without them. Streamline's interposer is not opened in N0.
- **macOS:** NGX has no Apple library, so on Apple targets `dlss` needs no SDK and compiles to
  a probe that always reports DLSS unavailable. The other vendor features are untested on
  macOS (`nrd` would need CMake and `dxc` there too); no macOS CI job builds them.

## Packaging the run-time binaries

Copy the binaries a feature loads **next to the executable**; the engine never searches the
system library path for them (a planted library elsewhere is ignored). On Windows they are
loaded with `LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR | LOAD_LIBRARY_SEARCH_DEFAULT_DIRS`, so their own
imports also come only from that directory and the system directories, never from `PATH` or
the working directory. Nothing checks a hash or signature at run time: the install directory
is trusted. Once opened, a vendor library stays loaded until the process exits (vendor DLLs
often do not survive being unloaded). NGX itself looks for the DLSS feature binary beside the
executable and in the driver. Do not ship any of them in a public release.

NGX keeps its logs and data in a per-user directory: `$XDG_CACHE_HOME/moba-engine/ngx` (or
`~/.cache/moba-engine/ngx`) on Linux, `%LOCALAPPDATA%\moba-engine\ngx` on Windows, beside the
client's pipeline cache. On Linux it is created with mode 0700 and refused (DLSS falls back)
if it is a symbolic link, not a directory, not owned by the process's effective user or
writable by others, or if its path is not UTF-8 (NGX takes it as a wide string).

**In a `dlss` build this happens on every machine**, AMD and Intel included: NGX's instance
query runs before `vkCreateInstance`, when the GPU is not known yet, so the directory is
created and NGX's (driver-free) instance query runs at every start-up. Only the device query
and NGX's initialisation wait for NVIDIA's own driver.

## Extensions before creation

ADR-0020 §1e: a back end's Vulkan extensions are declared before the instance and the device
exist. Before `vkCreateInstance`, NGX
(`NVSDK_NGX_VULKAN_GetFeatureInstanceExtensionRequirements`) names its instance extensions;
before `vkCreateDevice`, `NVSDK_NGX_VULKAN_GetFeatureDeviceExtensionRequirements` (on NVIDIA's
own driver only, since it loads the driver's NGX core) names its device extensions. XeSS's
`xessVKGetRequiredInstanceExtensions` and `xessVKGetRequiredDeviceExtensions` are queried by
its probe but not requested in N0: the probe never selects XeSS until N1 also merges its
device features, so enabling them would only widen every tiered device. The instance and the device enable each one the loader or the device
advertises; a missing one never fails creation. Device extensions are asked for on the tiered
path only (Compat changes only where shared code moves, ADR-0020 §2c), so DLSS, FSR 4 and
XeSS reject on Compat. A requested device extension is also dropped when enabling it would
make `vkCreateDevice` invalid:

- `VK_EXT_buffer_device_address` (the tiered path's core `bufferDeviceAddress` stands in);
- a name promoted to Vulkan 1.2 whose feature bit the device does not support
  (`VK_KHR_sampler_mirror_clamp_to_edge`, `VK_EXT_sampler_filter_minmax`,
  `VK_EXT_shader_viewport_index_layer`); when supported, the bit is set beside the name;
- a name whose device dependencies are not enabled, for the names in the dependency table in
  `device.rs` (`VENDOR_DEPENDENCIES`; others are taken to have none).

If `vkCreateDevice` still fails with vendor names in the list, the renderer logs one line and
retries once without them:

```text
[vendor] vkCreateDevice failed with the vendor extensions (…): <error>; retrying without them
```

Each probe repeats its queries and, when something is not enabled, rejects its back end with
its one line:

```text
[vendor] dlss unavailable: DLSS needs device extension VK_NVX_image_view_handle, which the device does not enable; upscaler falls back to builtin
```

In a `dlss` build NGX's instance list (before its core is loaded) is
`VK_KHR_get_physical_device_properties2`, which the instance then enables. FSR 4's API has no
requirement query.

**XeSS is never selected in N0.** Its required device *features*
(`xessVKGetRequiredDeviceFeatures`) can only be enabled at `vkCreateDevice`, and N0 does not
enable them. N1 merges them before `vkCreateDevice`, through a `vendor::device_features` hook
beside `vendor::device_extensions`, folding XeSS's standalone feature structures into the
renderer's `VkPhysicalDeviceVulkan12Features`/`VkPhysicalDeviceVulkan13Features` (chaining
them beside those is invalid, `VUID-VkDeviceCreateInfo-pNext-02830`). Until then, a probe that
finds the library and all its extensions still rejects it:

```text
[vendor] xess unavailable: XeSS 3.0.2 needs its required device features (xessVKGetRequiredDeviceFeatures), which are merged into the device in N1; upscaler falls back to builtin
```

**Streamline** must be loaded, and `slInit` called, before `vkCreateInstance`; it interposes
on the loader. N0 creates the instance without it, so the `streamline` probe only reports
whether `sl.interposer.dll` is installed, never loads it, and never selects frame generation;
that comes with N9.

## Selection and fallback

At renderer start-up each slot takes the first compiled-in back end the device supports, in the
order of the table above; later candidates for a filled slot are not probed. Every candidate
that is compiled in but unavailable logs **exactly one line**, then a summary follows:

```text
[vendor] dlss unavailable: NGX found no DLSS 310.9.16 feature binary (libnvidia-ngx-dlss.so.310.9.16) beside the executable or in the driver (NVSDK_NGX_Result_FAIL_FeatureNotFound); upscaler falls back to builtin
[vendor] selected: upscaler=builtin denoiser=builtin direct_lighting=rtxdi radiance_cache=sharc frame_generation=off latency=reflex compiled=dlss,… rtxdi=[…] sharc=[…]
```

The fallbacks are `builtin` (upscaler, denoiser, direct lighting), `none` (radiance cache) and
`off` (frame generation). The vendor checks read the driver as well as the PCI vendor: DLSS and
Streamline need NVIDIA's own driver (Mesa's NVK also reports vendor `0x10de` and is refused),
and FSR 4 needs AMD's own driver (RADV and AMDVLK are refused). FSR 4's RDNA 2 minimum has no
reliable device field, so the FidelityFX API checks it when N1 creates the context. The open build logs no `[vendor]` line. Reflex
(`VK_NV_low_latency2`) and Anti-Lag (`VK_AMD_anti_lag`) need no feature; `latency=` reports
which extension the device was **created with** (the tiered path enables
`VK_NV_low_latency2` only with `presentId`, never both latency extensions; Compat enables
neither, whatever the device advertises). Since N1d the renderer runs that back end and logs
one `[latency]` line either way (ADR-0021 §6 and amendment 3). `Renderer::vendor_backends()`
returns the same choice as data. The
selection is a trait object chosen inside `crates/render/src/vendor/`; no call site outside it
uses `cfg`.

The RTX 5070 Ti run with every Linux-buildable back end is in
[perf/0029](../perf/0029-vendor-sdks.md).

## Verification and CI

- `scripts/agent-verify.sh --full` checks `moba-engine --features sim,net,render,fsr3`
  (`--all-features` would need the SDKs), then clippy with each fetched feature alone and with
  all of them, the selection tests and an engine check. `nrd` is skipped unless `cmake
  --version` and `dxc --version` both run.
- The `vendor-sdks` CI job (Linux and Windows) sets up the pinned `slangc` (as every job that
  builds the shaders crate does), installs libclang and CMake, and takes `dxc` (and, on
  Windows, `glslc` and `spirv-val`) from the Vulkan SDK: on Linux from LunarG's tarball,
  checked against LunarG's published SHA-256 before unpacking, with `spirv-val` from
  `spirv-tools`; on Windows from Chocolatey's `vulkan-sdk` package at a pinned version. Only
  that subset is cached, keyed on the pin and the subset's version. It restores the archive
  cache keyed on `vendor-sdks.toml` (one entry for both OSes) and the NRD build cache (keyed
  on the runner image, the pins and `build/vendor.rs`; the stamp still decides reuse), each
  saved straight after the step that fills it, fetches and verifies `vendor-sdks,dlss-fg`,
  then builds and links `moba-client --features vendor-sdks,dlss-fg`, runs
  clippy and the selection tests (under `bash`, so each command's failure counts), runs clippy
  with each vendor feature alone (Linux), and checks that, with the vendor features on across
  the workspace, no server crate reaches `moba-render`, `bindgen`, `libloading` or `cmake`.
- **Type-checking the Windows code from Linux** (no MSVC needed; `cargo clippy` does not link):
  `rustup target add x86_64-pc-windows-msvc`, then `cargo clippy -p moba-render --lib --target
  x86_64-pc-windows-msvc --features dlss,rtxdi,sharc,fsr4,xess,nrd -- -D warnings` with
  `SLANGC` set to the fetched `slangc`, `BINDGEN_EXTRA_CLANG_ARGS_x86_64_pc_windows_msvc` set
  to `-ffreestanding -isystem <dir>` where `<dir>` holds stand-in `wchar.h`, `stdlib.h`,
  `string.h`, `cstdint`, `cstddef` and `cstring` that include `<stddef.h>`/`<stdint.h>`, and,
  for `nrd`, stand-in `cmake` and `VULKAN_SDK/Bin/dxc.exe` scripts with
  `CMAKE_GENERATOR=Ninja`. It catches what differs by target, such as C enums with values
  above `INT_MAX` (`NVSDK_NGX_Result`) being `int` under MSVC. `streamline` needs the real
  C++ standard library headers and is left out.
- `scripts/semver-check.sh` checks `moba-render` and `moba-engine` with their default
  features (plus `render` for the engine): `cargo-semver-checks` would otherwise turn the
  vendor features on and fail on the missing SDKs.
- `deny.toml` checks the `all-features` graph, which includes `bindgen`, `clang-sys`,
  `libloading`, `cmake` and their dependencies.

## Bumping an SDK

1. Change the entry's `tag`, `url`, `commit` and `version`; run the fetch. It fails on the
   archive hash: check the new archive came from the official repository, then update
   `sha256` (and `github_digest` where GitHub publishes one).
2. If the licence check fails, read the new licence in full, compare it with ADR-0020 §6a and
   `THIRD_PARTY.md`, and record the re-read in the PR before updating `licence_sha256`.
3. Re-run the build with the feature, the selection tests and, on a GPU, the fallback check.

## Notices and credits

`THIRD_PARTY.md` lists each feature's licence and obligations. The DLSS licence also asks for
NVIDIA marks in the in-game credits, splash screen and about box, and NVIDIA must be notified
before any commercial release (RELEASE.md step 8).

**Follow-up:** the client has no credits or about screen yet. When one is added, it must show
the notices and marks for every vendor feature compiled in (from `VendorBackends::compiled`).
